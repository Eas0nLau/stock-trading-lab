# 最终旧库数据补迁与删表设计

## 目标

冻结数据库写入后，将 16 张旧表的数据单向补充或更新到对应英文表，完整保留英文表独有数据。全部实时校验通过后，退役旧表运行时依赖并删除旧表。

## 数据所有权规则

- 旧表是本次补迁的输入，新表是最终事实源。
- 旧表有、新表没有的业务键插入新表。
- 两边业务键相同的记录，以旧表映射字段更新新表。
- 新表有、旧表没有的记录必须保留，迁移脚本不得删除。
- 禁止对新表执行 `DELETE`、`TRUNCATE`、全表替换或先清空后导入。
- 每张表使用 `INSERT ... ON DUPLICATE KEY UPDATE`，并在受控事务内执行。

## 执行阶段

### 1. 冻结和备份

停止 Web 服务、定时任务、采集器和其他数据库写入方。确认旧表与新表行数在观察窗口内不再变化后，使用 `mysqldump --single-transaction --routines --triggers --events` 创建带时间戳的全库备份，并确认备份文件非空且包含目标数据库 DDL。

### 2. 单向补迁

复用 `002_migrate_legacy_data.sql` 的字段转换规则，为全部 16 组映射执行可重跑的单向 upsert。当前已知缺口包括：

- `t_指数情绪周期_市场宽度` 到 `index_market_breadth`：`20260807`。
- `t_指数情绪周期_每日分析` 到 `index_emotion_daily`：`20260807`。
- `stock_basic` 到 `securities`：`301707.SZ`。
- `stock_daily` 到 `daily_quotes`：92,711 个旧表业务键。

补迁脚本仍覆盖全部 16 组，避免只修已知缺口而遗漏同键字段差异。

### 3. 实时包含校验

校验语义从“两表完全相等”调整为“新表完整包含旧表”：

- 每个旧表业务键在新表中的缺失数必须为零。
- 每个同键记录的全部映射字段必须一致。
- 旧表业务键必须唯一。
- 新表唯一键、JSON、外键和非空约束必须有效。
- 每张新表迁移后行数不得小于迁移前行数。
- 新表独有业务键的集合和数量不得减少。
- 每组 gate 结果写入结构化 `migration_validation_tables`，供删表 guard 复核，不能只依赖一条汇总状态。

任何一项失败都停止流程，不执行删表。

### 4. 退役旧表依赖

删除 `stock_lab.jobs.jiuyan_reconciliation` 对 `t_韭研公社异动解析` 的运行时读取，移除对应 legacy SQL 白名单。最终 parity 逻辑作为删表前一次性迁移边界保留，不进入正常应用运行路径。运行全量测试和应用启动检查，确认正式代码不读取或写入 16 张旧表。

### 5. 删除旧表

强化 `003_drop_legacy_schema.sql` 的前置条件，使其要求本次最新包含校验成功状态和 16 条表级通过记录。取得备份确认和破坏性操作授权后执行一次，删除 `schema_mapping.json` 中的 16 张旧表。MySQL DDL 不具备事务回滚能力，因此脚本执行期间不得中断。

### 6. 删除后验证

- 16 张旧表均不存在。
- 所有英文表行数与删表前一致。
- 新表独有键仍存在。
- API、定时任务和关键 CLI 启动正常。
- 全量测试通过。
- Redis 现有业务 key 仍可由 MySQL 重建。

## 回滚

补迁阶段只 upsert，不删除新表数据；失败时回滚当前事务并修复映射。旧表删除后若验证失败，停止应用并从本次全库备份恢复，不尝试手工重建部分旧表。

## 明确不做

- 不删除任何新表数据。
- 不把新表回写到旧表。
- 不依赖 2026-08-07 的历史 `002_parity_v1` 结果授权删表。
- 不把 Redis 内容作为补迁来源。
